Why I built Resident

I wanted to put the model on my phone to work.

I build AI agents for a living. When I started trying local models on my phone, I wanted to give them the kinds of tasks I already used AI for: research, files and work in other apps.

The apps I tried kept getting in the way. Some ran models well but gave them few ways to act. Others offered tools without managing the context a small model needs to use them.

So I built Resident around the whole task: finding the right tool, getting useful information back, recovering from a bad call and continuing to the next step. Then I worked on making that loop fit the memory and compute available on a phone.

The goal is to get as much useful work as possible out of the model that fits in your pocket.

Justin Flick · Creator of Resident

Built around the limits of a phone

The harness makes room for the work.

A model that fits on a phone has little room to waste. Resident manages the tools, context and execution around it so more of that capacity goes toward your request.

The constraint What Resident does Why it matters
Too many tools, too little context Lists connectors briefly, opens relevant tools on demand and trims their definitions. More room for your request and the information needed to answer it.
Results too large to use Shortens structured results, reads files in parts and selects relevant passages from web pages. The next step gets useful context within a limited budget.
Tool calls that go wrong Returns errors the model can act on and constrains tool-call syntax for supported models. A chance to correct the call and continue the task.
Repeated work between steps Reuses cached context and saves progress after each completed step. Less repeated processing, and a way to resume interrupted work.

Measured with the same model and the same tasks.

One before-and-after comparison used LFM3 1.7B on 387 shared test cases. After a round of harness fixes, it passed 374, up from 357.

These are controlled tests on a Mac: external services are simulated, and pull request cases use a small fixture repository. They measure behavior inside the harness, not a success rate for arbitrary real-world work. Individual runs vary.

Inside the engineering

Tools arrive when the task needs them

A connector starts as one line in the prompt. When needed, Resident exposes a small set of relevant tools and trims their descriptions and schemas. Skills follow the same principle: make the capability discoverable, then load its instructions when they are useful.

File tools keep code changes manageable

The model lists, searches, reads and edits local files. With GitHub connected, the harness handles downloading a repository and turning changed files into a branch, commit and pull request. The model can focus on the edit without assembling that sequence of GitHub API calls. The code sandbox is separate: it runs JavaScript with no network or file access.

Error recovery is part of the loop

Unrecognized tools and malformed calls return feedback the model can use to try again. For supported tagged-JSON formats, including Qwen 3, a decoder grammar restricts tool names and arguments to the declared schema. Other formats, including LFM3, use parsing and error feedback. This helps with call structure; it does not guarantee the model chooses the right action.

Making room for a 27B model on a 12 GB iPhone

Bonsai 2 27B has 8.6 GB of weights. Supporting it on the tested 12 GB iPhone required changes to the inference library: mapping aligned weights from their file, pinning pages during a reply, and custom Metal kernels that avoid loading 420 MB of redundant biases.

It runs at about 7 tokens a second and slows during longer replies. LFM3 1.7B runs at about 65 on that phone. The larger model is an option for exploring what fits; the smaller one is the recommended starting point. Resident checks fit before download and chooses a suitable build for your device.

Local by design

The model lives on your phone. You choose its connections.

With an on-device model, inference happens on your hardware. Your conversations are stored on the device. There is no Resident account, analytics or inference server.

Work offline

After downloading a model, chat and local tools can run without a connection or a per-message inference fee.

Connect deliberately

Web tools send searches and page requests. Connected services receive tool arguments. You choose which tools each agent can use.

Get Resident

Build it today. Put it to work.

Resident is available as source today, with an App Store release coming soon. You need a Mac with Xcode and a real iPhone or iPad to run downloaded models on the device. 

git clone https://github.com/jflick58/resident.git
cd resident
brew install xcodegen
cp Config/Local.xcconfig.example Config/Local.xcconfig

Set your Apple team ID, bundle ID and device name in Config/Local.xcconfig, then run ./run-device.sh to build and install. Choose a model in the app, download it and try a focused task.
