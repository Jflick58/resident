Small model. Serious agent.

Resident puts an AI agent on your iPhone, powered by models that run on the device. It can research a question, work with your files and take action in the apps you connect, using tools across several steps to carry out what you asked.

Tools, skills, memory and an agent harness engineered for small models. Open source.

What it can do

A real harness, not a chat app.

If you use Claude Code or Codex, the loop will be familiar: read, act, check the result, carry on. Resident runs that loop on a phone, and not only for code.

Works on your files

The tools a coding agent has: list, search, read, edit and write. They work on a folder you can see in the Files app, so you can put files in and take out what it wrote.

Ships pull requests

With GitHub connected it clones a repository, changes the code and opens a pull request for you to review. The branch and the commit are made for it.

Runs code

A JavaScript sandbox on the device, with no network and no access to your files. Arithmetic, dates and data are computed, not guessed.

Reads the web

Search and page reading run on the phone, with no account or key. A long page is ranked against the question, so only the passages that matter are read.

Loads skills

Saved instructions for one kind of job, loaded only when a request matches. Import a SKILL.md, or turn something it just did into a skill with one tap.

Remembers

A short list of lasting facts about you, used in later chats. You can read it, edit it or switch it off.

Knows your day

Reads your calendar and reminders, adds to them and checks reminders off, through iOS itself on the device.

Takes the shape you give it

An agent is a set of instructions and a switch for each tool. Start with Assistant or Coder, or write your own.

Connectors

Works in the services you use.

GitHub, Linear, Notion, Atlassian, Sentry, Hugging Face and DeepWiki are in the list. Any other service that speaks the Model Context Protocol (MCP) is added by pasting its address.

You sign in on the service’s own page, as you would for any app. Resident never sees your password, keeps its access in the iPhone’s Keychain and renews it without asking again.

Automations

Put an agent on a schedule.

Ask Resident is an action in Shortcuts. Give it a message, an agent and a model, and it runs with the app closed and hands the reply to the next action as plain text.

So an agent can be a step in anything Shortcuts runs. Connect your tools, save a skill that pulls out what you care about, and have it run every morning: real agent work, done by a model on your phone.

Why local

The model runs on your phone. You control its connections.

Local inference does not send your conversation to a model provider. Web searches and connected services receive the information needed for the tools you enable.

Private

Every token is computed by the chip in your pocket. There is no account and no analytics, and Resident has no server for a conversation to go to. What you write goes out only when a tool sends it, and every tool has a switch.

No data center

It works offline, it costs nothing per message, and it keeps working whatever happens to somebody else’s API.

Wired into your device

Calendar, Reminders, the Files app and Shortcuts are within reach through iOS itself, with no service in between.

Why I built it

I wanted local AI I could put to work.

I build AI assistants for a living. When I started trying models on my phone, I wanted to see how far they could go.

The apps I tried kept getting in the way. Some offered little beyond conversation. Others exposed tools without doing enough to help a small model choose and use them.

So I built Resident: an app that brings together the tools, context management, memory and execution loop those models need to carry out useful tasks.

The work has been in the details: keeping tool definitions small, making failures recoverable, and getting each step to run efficiently on a phone. Resident is where I am putting that work into practice.

Engineering

Small models need carefully designed tools.

A small model can reason well and still fall over on a real task. It drowns in a big set of tools, loses its place between steps, or writes a call nothing can parse. Each part of Resident’s harness answers a failure like that.

What goes wrong What Resident does What you get
Tool definitions fill the context before the task starts Shows one line per connector, opens only the tools a request needs, and trims their definitions Room for the task itself
A task takes several tool calls Feeds each result back to the model, and saves the chat after every step Work that carries across steps, and carries on if iOS cuts it off
The model makes a bad call Returns an error it can act on, loads the tool it meant, and for JSON tool calls holds the decoder to a grammar A model that recovers instead of stalling
Every step rereads the whole chat Keeps the start of the prompt fixed, so the model’s cache of it stays good and each step reads only what is new Less waiting between steps
The model you want does not fit the phone Checks fit before download, picks the build that suits the device, and maps weights too big to load No trial and error, and room for larger models

How this is checked. A public test suite runs any model through the same harness as the app. The services in it are simulated and its pull request cases use one small made-up repository, so it tests the model and the harness. On its last full run, LFM3 1.7B passed 382 of 398 cases.

The details, for those who want them

Tools are disclosed a step at a time

The prompt lists your connectors, a line each. The model picks a connector when a request needs it, and is then given the tools in it that fit what it asked for. A big MCP server costs one line until it is used.

Tools shaped like a coding agent’s

Small models have seen list, search, read and edit endlessly. They have not seen GitHub’s API. So the model works on files with the tools it knows, and the branch, the commit and the pull request are the harness’s job.

Autocorrect for tool calls

A tool called by the wrong name is answered with the closest real ones, ready to call. A call with the wrong arguments comes back with the ones it needed, and a wrong file path with the right one. The model reads the correction and carries on. For models that write tool calls as JSON, a grammar on the decoder rules out a malformed call altogether.

Prompt caching, kept on the phone

The start of the prompt never changes, so the model’s cache of it stays good and each step reads only what is new. The instructions and tools that open every chat are read once and stored beside the model, so a new chat starts from that copy. For a large model that saves most of a minute. Tools opened in the middle of a chat are declared where the conversation stands, which leaves the cache as it was.

Builds chosen by measurement

The eval harness compares every quantized build of a model with its full-precision weights, token by token. The 4-bit LFM3 picks the same next token 89.5% of the time and the 6-bit 97.3%, so the app offers the 6-bit wherever it fits.

Each piece is written up, with the file to read for it, in the harness notes.

Pushing the phone

A 27B model on a 12 GB iPhone.

iOS lets an app use about half of the phone’s memory. The weights of Bonsai 2 27B are 8.6 GB. Running it, and keeping it running past the first reply, meant changing the inference library itself.

Weights mapped, not loaded

The weights file is rearranged in place so every large tensor starts on a page boundary, then mapped read-only. The GPU reads the file’s own pages, which iOS does not charge to the app.

Pinned while it works

iOS takes mapped weights back whenever memory runs short, and the model has to read them from storage again before it can answer. Without a fix, the 27B’s second reply took over a minute to start. So the weights are pinned in memory while a reply is written, and released after it.

420 MB that never loads

In a ternary model every bias is its scale negated, so the biases hold nothing new. Custom Metal kernels compute those layers without them, and 420 MB of the 27B never has to be in memory.

On an iPhone Duo, Bonsai 2 27B ran at about 7 to 10 tokens a second on short replies and slower on long ones. LFM3 1.7B (6-bit) ran at about 65. Mapping is automatic for models too big to fit in memory. The changes are a fork of mlx-swift-lm, listed in the repository.
