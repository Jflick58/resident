Why local

Your phone is enough.

A model that runs where you are is one you can hand your files, your calendar and your work to.

Private

The model, your chats, your files and what it remembers about you stay on the phone. There is no account, no analytics, and no server of ours for anything to go to.

No data center

Every token is computed by the chip in your pocket. It works offline, it costs nothing per message, and it keeps working whatever happens to somebody else’s API.

Wired into your device

Calendar, Reminders, the Files app and Shortcuts are within reach. So are your services: GitHub, Linear, Notion, and anything else that speaks MCP.

Under the surface

It looks like a chat app. Most of it is underneath.

What you see is a message box and a model’s name. What makes it work is the part you do not see, and the further down you go, the more of an engineering project it gets.

Depth 1 The harness

A real harness, not a chat app.

If you use Claude Code or Codex, you know the loop: read the code, make the change, ship it. Resident runs that loop on a phone, with a model small enough to live there.

Works on your files

The tools a coding agent has: list, search, read, edit and write. They work on a folder you can see in the Files app, so you can put files in and take out what it wrote.

Ships pull requests

With GitHub connected it clones a repository, changes the code and opens a pull request for you to review. The branch and the commit are made for it.

Speaks MCP

GitHub, Linear, Notion, Atlassian, Sentry, Hugging Face and DeepWiki are in the list. Any other MCP server is added by its address, with sign-in on the service’s own page.

Runs code

A JavaScript sandbox on the device, with no network and no access to your files. Arithmetic, dates and data are computed, not guessed.

Reads the web

Search and page reading run on the phone, with no account or key. A long page is ranked against the question, so only the passages that matter are read.

Loads skills

Saved instructions for one kind of job, loaded only when a request matches. Import a SKILL.md, or turn something it just did into a skill with one tap.

Remembers

A short list of lasting facts about you, used in later chats. You can read it, edit it or switch it off.

Takes the shape you give it

An agent is a set of instructions, a switch for each tool and a thinking level. Start with Assistant or Coder, or write your own.

Runs from Shortcuts

Ask Resident puts an agent inside your automations with the app closed, and shows a long job as a Live Activity you can stop.

Also in there: Calendar and Reminders through iOS itself, photos, PDFs and documents as attachments, and dictation by a speech model that runs on the device.

Depth 2 Harness engineering

Reliability from a stupidly small model.

A 1.7B model reasons well and falls over easily. It drowns in a big MCP server, forgets a tool’s name, and will happily reread its whole context at every step. Each piece below is there because a transcript showed a small model failing without it.

A big MCP server costs one line

A connector is one line in the prompt until a request needs it. Then the model gets the six tools that best fit what it asked for, not the whole server; Linear’s has about 70. In our Linear tests, declaring every tool up front made an 18,600-token prompt and the model finished 10 of 12 tasks. Opened on demand it took under 3,000 tokens and finished 12 of 12.

Tool definitions, rewritten

Services describe their tools for large models. Resident cuts every description and schema down to what it takes to make the call. 5,500 tokens of opened tools became under 3,000, and tasks ran a third faster.

The prompt is read once

The start of the prompt never changes, so the model’s cache of it stays good and each step reads only what is new. Tools opened in the middle of a chat are declared where the conversation stands, not back at the top.

Results are fitted, not cut off

Twenty issues with pages of description would fill the context. A structured result is shortened field by field with every item kept, a long file is read a part at a time, and a result the model has already seen is named instead of sent again.

Tools shaped like a coding agent’s

Small models have seen list, search, read and edit endlessly. They have not seen GitHub’s API. So the model gets the tools it knows, and the branch, the commit and the upload are the harness’s job. Given GitHub’s own tools, a 9B model finished 7 of 13 pull request tasks. This way a 1.7B finishes 23 of 23.

Mistakes come back with the fix

A tool called by the wrong name loads the closest real ones. A failed call returns the parameters it needed, and a call that cannot be parsed comes back as an error the model can read. A model still searching after it has found the place is told to make the change or ask.

A grammar on the decoder

For models that write tool calls as JSON, such as Qwen 3, the decoder is held to a grammar the moment a call opens. Only a declared tool’s name can follow, and the arguments must match its schema token by token. Text and thinking stay free.

Tested like software

A public suite of 423 scored requests runs any model through the same harness as the app, and LFM3 1.7B passed 382 of 398 on its last full run. A chat that goes wrong on a phone is copied off it and replayed on a Mac until the harness gets the model through.

The suite and its results and a write-up of each piece are in the repository.

Depth 3 Custom inference

A 27B model on a 12 GB iPhone.

iOS lets an app use about half of the phone’s memory. The weights of Bonsai 2 27B are 8.6 GB. Running it, and keeping it running past the first reply, meant changing the inference library itself.

Weights mapped, not loaded

The weights file is rearranged in place so every large tensor starts on a page boundary, then mapped read-only. The GPU reads the file’s own pages, which iOS does not charge to the app.

Pinned while it works

Mapped pages are the first thing a phone short of memory takes back. Left alone, the 27B’s second reply had not started after 70 seconds of reading its weights in again. So what the model has read is pinned for the length of a reply, then let go.

420 MB that never loads

In a ternary model every bias is its scale negated: a tenth of the file with nothing new in it. Our own Metal kernels compute those layers without the biases, so that tenth never has to be in memory.

A prompt already read

The instructions and tools that open every chat are read once and saved beside the model. A new chat starts from that copy, which for a large model saves most of a minute.

A cache that never rewinds

These models cannot back their cache up, so one token rendered differently means reading the whole prompt again: two minutes for a 27B. Turns are kept exactly as the model wrote them, so it never has to.

Rounding, measured

Every quantized build is compared with the full-precision weights token by token. The 4-bit LFM3 picks the same next token 89.5% of the time and the 6-bit 97.3%, so the app offers the 6-bit wherever it leaves room for a full-length chat.

Where that leaves it: Bonsai 2 27B answers at about 7 tokens a second on a 12 GB iPhone and slows as a reply runs long. LFM3 1.7B runs at about 65. The changes are a fork of mlx-swift-lm, listed in the repository.
